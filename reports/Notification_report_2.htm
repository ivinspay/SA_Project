Interaction: Delivery Result

1. Elevation by Changing the Execution Flow in Zulip Server  [State: Mitigation Implemented]  [Priority: High] 

Category:Elevation Of Privilege
Description:An attacker may pass data into Zulip Server in order to change the flow of program execution within Zulip Server to the attacker's choosing.
Justification:The push service checks that all input matches the expected format and rejects anything tampered with or invalid, and it forwards the encrypted notification without opening it, so attackers can’t use the data to change how the service runs.

2. Zulip Server May be Subject to Elevation of Privilege Using Remote Code Execution  [State: Mitigation Implemented]  [Priority: High] 

Category:Elevation Of Privilege
Description:Push Notification Service may be able to remotely execute code for Zulip Server.
Justification:The push service only accepts authenticated requests from registered servers, checks every field against an expected format, and passes along the encrypted notification without ever opening or running it

3. Elevation Using Impersonation  [State: Mitigation Implemented]  [Priority: Medium] 

Category:Elevation Of Privilege
Description:Zulip Server may be able to impersonate the context of Push Notification Service in order to gain additional privilege.
Justification:Communication is one-directional, the Zulip server initiates authenticated HTTPS requests to the Push Notification Service

4. Data Flow Delivery Result Is Potentially Interrupted  [State: Mitigation Implemented]  [Priority: Low] 

Category:Denial Of Service
Description:An external agent interrupts data flowing across a trust boundary in either direction.
Justification:If the push service crashes or slows down, only phone notifications are delayed

5. Potential Process Crash or Stop for Zulip Server  [State: Mitigation Implemented]  [Priority: Low] 

Category:Denial Of Service
Description:Zulip Server crashes, halts, stops or runs slowly; in all cases violating an availability metric.
Justification:If the push service crashes or slows down, only phone notifications are delayed

6. Data Flow Sniffing  [State: Mitigation Implemented]  [Priority: Medium] 

Category:Information Disclosure
Description:Data flowing across Delivery Result may be sniffed by an attacker. Depending on what type of data an attacker can read, it may be used to attack other parts of the system or simply be a disclosure of information leading to compliance violations. Consider encrypting the data flow.
Justification:Notifications travel over an encrypted HTTPS connection, and the message content inside is also encrypted so only the user’s phone can read it, so anyone listening in, including the push service itself, sees only scrambled data.

7. Potential Data Repudiation by Zulip Server  [State: Mitigation Implemented]  [Priority: High] 

Category:Repudiation
Description:Zulip Server claims that it did not receive data from a source outside the trust boundary. Consider using logging or auditing to record the source, time, and summary of the received data.
Justification:Each request between the Zulip Server and Push Notification Service is authenticated and returns an explicit success/error response

8. Cross Site Scripting  [State: Not Applicable]  [Priority: Low] 

Category:Tampering
Description:The web server 'Zulip Server' could be a subject to a cross-site scripting attack because it does not sanitize untrusted input.
Justification:The Push Notification Service is a JSON-only REST API that forwards notifications to FCM/APNs, and it does not render data into HTML for browsers, so there is no XSS sink on this flow.

9. Potential Lack of Input Validation for Zulip Server  [State: Mitigation Implemented]  [Priority: Medium] 

Category:Tampering
Description:Data flowing across Delivery Result may be tampered with by an attacker. This may lead to a denial of service attack against Zulip Server or an elevation of privilege attack against Zulip Server or an information disclosure by Zulip Server. Failure to verify that input is as expected is a root cause of a very large number of exploitable issues. Consider all paths and the way they handle data. Verify that all input is verified for correctness using an approved list input validation approach.
Justification:The delivery result arrives over an encrypted HTTPS connection that the server checks with the push service’s certificate, so it can’t be changed in transit

10. Spoofing the Zulip Server Process  [State: Mitigation Implemented]  [Priority: Low] 

Category:Spoofing
Description:Zulip Server may be spoofed by an attacker and this may lead to information disclosure by Push Notification Service. Consider using a standard authentication mechanism to identify the destination process.
Justification:The push service only accepts requests from registered Zulip servers that sign in with their own secret key over an encrypted connection

11. Spoofing the Push Notification Service Process  [State: Mitigation Implemented]  [Priority: Low] 

Category:Spoofing
Description:Push Notification Service may be spoofed by an attacker and this may lead to unauthorized access to Zulip Server. Consider using a standard authentication mechanism to identify the source process.
Justification:The server starts every connection, to a configured address and Zulip&#39;s server checks outgoing HTTPS certificates.

12. Spoofing of Destination Data Store Device Token Registry  [State: Mitigation Implemented]  [Priority: Low] 

Category:Spoofing
Description:Device Token Registry may be spoofed by an attacker and this may lead to data being written to the attacker's target instead of Device Token Registry. Consider using a standard authentication mechanism to identify the destination data store.
Justification:The registry is an internal PostgreSQL database with authenticated connections.

13. Potential Excessive Resource Consumption for Push Notification Service or Device Token Registry  [State: Mitigation Implemented]  [Priority: Medium] 

Category:Denial Of Service
Description:Does Push Notification Service or Device Token Registry take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:API-endpoints are rate-limited and push notifications are sent asynchronously from a queue with timeouts and retries.

14. Data Flow Sniffing  [State: Mitigation Implemented]  [Priority: Medium] 

Category:Information Disclosure
Description:Data flowing across Device Token may be sniffed by an attacker. Depending on what type of data an attacker can read, it may be used to attack other parts of the system or simply be a disclosure of information leading to compliance violations. Consider encrypting the data flow.
Justification:Device tokens are encrypted on the device and only decrypted inside the push notification service.

15. Data Store Denies Device Token Registry Potentially Writing Data  [State: Mitigation Implemented]  [Priority: Low] 

Category:Repudiation
Description:Device Token Registry claims that it did not write data received from an entity on the other side of the trust boundary. Consider using logging or auditing to record the source, time, and summary of the received data.
Justification:PostgreSQL acknowledges each committed write to the application

Justification:Tokens are encrypted on the device with authenticated encryption so any tampering in transit fails decryption and is rejected
